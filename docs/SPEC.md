# 專案：幼童軍進程與技能章查詢系統

你是這個專案的長期維護工程師。

第一件事：把這整份規格原文存成 docs/SPEC.md 並 commit。之後我只會說「照 SPEC.md 做」或「SPEC.md 第幾節要改成……」，規格有變動時你要同步更新 SPEC.md。

請先讀完整份規格，再依「十三、工作方式」分階段進行。全程用繁體中文與我溝通，程式碼註解也用繁體中文。

## 一、目的
- 小狼（幼童軍）和家長：從 LINE 官方帳號開啟網頁，查入團時間、已拿到與正在挑戰的進程和技能章、還有哪些待挑戰。實際操作的人多半是家長。
- 團長與服務員：同一個入口進後台，管理名單、產生綁定碼、簽核完成項目、登錄頒章。
- 團長可以不改程式就指定管理員、調整項目內容、說明文字與各項系統數值。
- 晉級與頒章不自動執行，但條件一滿足要由 LINE 官方帳號主動通知團長；頒發日期由團長設定並記錄。
- 對象是未成年人，個資保護與可刪除性是硬需求，不是加分項。

## 二、技術架構
- 前端：web/index.html（原生 HTML/CSS/JS + LIFF SDK，不用框架、不用建置工具），部署到 GitHub Pages。查詢端與後台同一頁，依身分顯示不同畫面。
- 後端：Google Apps Script Web App，用 clasp 管理與部署。原始碼放 gas/，可拆成多個 .gs 檔。
- 資料庫：Google 試算表。
- LINE：一個 LINE Login channel（掛 LIFF）＋一個 Messaging API channel（官方帳號），兩者必須在同一個 Provider 底下，userId 才一致。LIFF 開啟「加入好友選項」。
- 已知限制，請照這樣處理：
  1. 前端呼叫 GAS 用 fetch POST，Content-Type 設為 text/plain 並在 body 放 JSON，避免 CORS 預檢失敗。
  2. GAS 的 doPost 讀不到請求標頭，無法驗證 X-Line-Signature。改為 webhook 網址帶一個長隨機密鑰參數（存在 Script Properties），不符就直接忽略；並且只處理事件內容格式正確的請求。
  3. doPost 同時接 LIFF 前端 API 與 LINE webhook，依密鑰參數與 body 結構分流。
  4. 單次執行不可超過 GAS 6 分鐘上限；試算表一律批次讀寫（getValues/setValues），不逐格讀寫；寫入用 LockService。
  5. LIFF 的 ID token 會過期，在 LINE 內可能拿到舊的。後端驗證失敗且原因是過期時，回傳明確的錯誤代碼；前端收到後自動重新登入取得新 token 並重送一次，不要讓使用者看到錯誤畫面。
  6. GitHub Pages 的 repo 可能是公開的。前端只能有 LIFF ID 與 GAS 網址，其餘一律不得出現在 repo。
- 以上第 2、5 點與「LINE webhook 打到 GAS 能穩定運作」是尚未驗證的假設，必須在階段 0 實測，不通就停下來跟我討論替代方案，不要硬做下去。

## 四、試算表結構
由 setup() 一鍵建立所有分頁與標題列。setup() 可重複執行，任何分頁已有資料時一律不覆蓋、不重新匯入。
- 小狼名單：小狼ID、姓名、小隊、入團日、目前級別、綁定碼、綁定碼剩餘次數、狀態（在團/離團/已匿名）、離團日
- 綁定紀錄：LINE userId、LINE 顯示名稱、小狼ID、綁定時間、同意時間、同意版本
- 管理員：LINE userId、姓名、LINE 顯示名稱、角色（團長/服務員）、加入時間、指定人
- 管理員邀請：邀請碼、角色、姓名、建立人、建立時間、到期時間、狀態（未使用/已使用/已作廢）、使用者 userId、使用時間
- 項目總表：項目ID、類別（進程/技能章）、級別或章名、大項、項目內容、排序、啟用（是/否）
- 級別與章說明：名稱、類別（進程/技能章）、分類（服務類/健身類/技巧類，進程留空）、說明、晉級條件、排序
- 完成紀錄：小狼ID、項目ID、完成日期、簽核人、備註、回報人、回報狀態
- 頒章紀錄：小狼ID、級別或章名、頒發日期、頒發場合、備註、簽核人、登錄時間
- 通知紀錄：小狼ID、級別或章名、通知類型、通知時間
- 綁定失敗紀錄：LINE userId、時間
- 告知同意內容：版本、內容、生效日
- 設定：鍵、值、說明
- 操作日誌：時間、操作人、動作、對象、修改前、修改後

「完成紀錄」的回報人、回報狀態兩欄是為第二期「家長回報」預留，第一期一律留空，但所有讀寫程式都要能正確帶過這兩欄。

項目資料的來源：
- setup() 第一次執行時把 data/items.csv 匯入「項目總表」，把第十二節的進程晉級條件匯入「級別與章說明」（技能章說明留空，我之後自己填），並把 docs/PRIVACY.md 的預設告知文字寫入「告知同意內容」作為第 1 版。
- 匯入之後，試算表才是唯一來源，之後的修改都在後台或試算表進行，不需要動程式碼、不需要重新部署。
- 項目ID 規則要穩定且可讀（例如 P-狼-國旗-1、B-嚮導-1），由後端產生，一經產生永不更改、永不重用。

## 五、狀態定義與達標判定
每一個進程級別、每一個技能章，對每位小狼都只有四種狀態，查詢端與後台統一使用：
- 已頒發：頒章紀錄有這一筆。顯示頒發日期。
- 已完成待頒發：啟用中的項目全部完成，但尚未頒章。
- 進行中：至少完成 1 項但未全部完成。
- 未開始：0 項完成。
進程另有規則：目前級別的下一級，即使 0 項完成也視為「進行中」。

達標（可頒章）判定：
- 羚羊級：該級啟用項目全部完成即達標（團集會次數由團長人工確認）。
- 狼、鹿、豹級：該級啟用項目全部完成，且距上一級的「頒發日期」滿設定的晉級間隔月數。以頒發日期起算，不是登錄時間。
- 技能章：該章啟用項目全部完成。
- 停用的項目不計入完成度與達標判定。
- 達標只代表「可頒章」，不改變任何資料，一律等團長登錄頒章。

## 六、查詢端（家長/小狼）
1. 第一次開啟：輸入綁定碼 → 顯示個資告知同意畫面 → 勾選同意後才完成綁定。
   - 告知畫面內容取自「告知同意內容」最新版，用家長看得懂的白話說明：蒐集哪些資料（孩子姓名、小隊、入團日、進程紀錄、家長的 LINE 顯示名稱）、誰看得到（團長與服務員）、存放在哪裡、保存多久、如何要求更正或刪除、聯絡誰。
   - 不同意就不綁定，也不留下任何紀錄。
   - 同意時間與版本寫入綁定紀錄。告知內容改版後，已綁定的帳號下次開啟時要重新確認一次。
   - 一個 LINE 帳號可綁多位小狼，一位小狼可被多個帳號綁定。綁多位時上方可切換。
2. 首頁由上到下（最重要的放最上面，先回答家長「我的孩子下一步要做什麼」）：
   - 基本資料：姓名、小隊、入團日、入團至今多久（X 年 X 個月）、目前級別。
   - 「下一步挑戰」：列出下一級尚未完成的 3 個項目。
   - 「正在挑戰的」：進行中與已完成待頒發的進程級別與技能章，每一筆顯示名稱、說明、完成幾項/共幾項、進度條，點開看逐項狀態與各項完成日期。
   - 「已經拿到的」：已頒發的進程級別與技能章，依頒發日期由新到舊，每一筆顯示名稱、頒發日期、說明。
   - 「還沒開始的」：預設收合，展開可瀏覽全部未開始的技能章與說明。
3. 已完成待頒發的狀態，查詢端文字為「項目已全部完成，等待團長評核頒發」，不顯示「可晉級」字樣。
4. 進程頁：羚羊→狼→鹿→豹四張卡片，顯示狀態、晉級條件、完成幾項/共幾項，點開依大項看逐項「已完成（含日期）/待挑戰」。
5. 技能章頁：依服務類/健身類/技巧類分組，每章顯示狀態與說明，點開看合格標準逐項狀態。
6. 說明文字留空時，該處不顯示空白區塊。
7. 「我的資料」頁：顯示目前綁定的小狼、同意的版本與時間、告知內容全文，並提供「解除綁定」按鈕與「如何要求刪除資料」的說明。
8. 列印：進程頁提供「列印這一級的簽核單」，產生適合 A4 列印的頁面（項目、完成日期、簽核人、未完成的留空格），讓家長可以夾進紙本手冊。
9. 介面：手機優先、字大按鈕大、小學生看得懂。配色用童軍風格的黃與藍，活潑但不花俏。不依賴外部圖片。

## 七、團長後台
身分判斷：後端驗證後的 userId 存在「管理員」分頁才可進後台。

權限：團長可做全部操作。服務員只能簽核、撤銷自己的簽核、查看名單與總覽、列印簽核單；不可管理名單、綁定碼、管理員、項目、設定、個資處理，也不可頒章。

身分並存：同一個 LINE 帳號可以同時是管理員又綁定了小狼。這種帳號開啟 LIFF 時預設進後台，畫面上方有「切換到家長畫面」的按鈕。

### 7.1 首頁
- 最上方固定顯示「待頒章」名單與數量，以及「快達標」名單（依設定門檻）。
- 顯示系統提示：通知未送達、項目總表格式錯誤列數、設定值不合理、上次備份時間與是否成功、離團已超過設定天數尚未處理個資的小狼。

### 7.2 小狼管理
- 新增/編輯/標記離團。入團日由團長填寫，可填過去日期。新增時由後端自動產生綁定碼。標記離團時記錄離團日，綁定碼立即失效。
- 列表顯示入團日，可依入團日或小隊排序篩選。

### 7.3 綁定碼
- 後端產生亂碼，長度依設定，只用大寫英文與數字並排除易混淆字元（0、O、1、I、L），保證不重複。可用次數依設定，用完失效。
- 後台可重新產生（舊碼立即失效）、查看誰綁了這位小狼、解除某個綁定，並提供「複製給家長的說明文字」按鈕。

### 7.4 簽核
簽核是服務員在團集會現場用手機操作的功能，速度優先：三步內完成、不需要打字、送出後留在原畫面可繼續簽下一批。
- 小隊批次簽核（主要用法）：選小隊（或全團）→ 勾選一個或多個項目 → 勾選一位或多位小狼（預設全選該小隊，可取消個別）→ 填日期（預設今天）→ 一次送出。已完成的組合自動略過不重複寫入，送出後顯示「新增幾筆、略過幾筆」。
- 單人簽核：選小狼→看到全部啟用項目→勾選完成並填日期，簽核人自動帶入。
- 項目選擇要好找：可依級別與大項篩選，並把「最近簽過的項目」放最上面。
- 撤銷簽核：可取消誤簽，寫入操作日誌。剛送出的那一批提供「復原」按鈕。
- 總覽：小狼×級別的完成度矩陣，可依小隊篩選。
- 列印簽核單：可依小狼或依小隊，列印某一級的簽核單（A4），供貼進或夾進紙本手冊。

### 7.5 頒章（頒發日期由團長設定）
- 頒章表單欄位：頒發日期（必填，預設今天，可改）、頒發場合（選填，例如「11 月團集會」）、備註（選填）。簽核人自動帶入。
- 頒發日期可填過去日期，不可早於該級別或該章最後一個項目的完成日期；填未來日期時要再確認一次。
- 頒發日期是儀式實際日期，登錄時間是系統寫入時間，兩者分開存。
- 批次頒章：同一場儀式可勾選多位小狼、多個級別或技能章，共用同一個頒發日期與場合，一次送出。
- 進程頒章成功後更新該小狼的目前級別。
- 修改與撤銷：團長可修改已登錄的頒發日期、場合、備註，也可撤銷整筆頒章（撤銷進程頒章後目前級別退回上一級）。兩者都寫入操作日誌並保留修改前的值。
- 頒發日期被修改或頒章被撤銷時，重新計算受影響小狼的達標狀態。

### 7.6 直接補登頒章（系統上線時用）
現有團員多半已有級別與技能章，不逐項補勾：
- 選小狼 → 選級別或技能章 → 填頒發日期 → 送出，直接寫入頒章紀錄。
- 同時把該級別或該章的所有啟用項目標記為完成，完成日期填頒發日期，備註註明「上線補登」。
- 補登進程級別時，較低級別若沒有紀錄，提示我是否一併補登。
- 補登不觸發任何推播通知。

### 7.7 項目管理（團長專用）
- 依「進程/技能章 → 級別或章名 → 大項」樹狀瀏覽全部項目。
- 修改項目內容文字：直接編輯存檔，項目ID 不變，既有完成紀錄保留。
- 新增項目：選擇所屬級別或章名與大項，輸入內容，項目ID 由後端自動產生。
- 停用項目：不刪除，只把「啟用」設為否。停用後不顯示於查詢端、不計入完成度與達標判定，完成紀錄保留，重新啟用即恢復。項目不提供真正刪除。
- 調整順序：同一大項內可上移/下移，只改「排序」欄。
- 新增技能章或大項；修改技能章名稱或大項名稱時同步更新其下所有項目，項目ID 不變。
- 編輯「級別與章說明」的說明與晉級條件文字。
- 影響預覽：會影響達標結果的操作（新增、停用、重新啟用項目），送出前先顯示「這會讓 N 位小狼從已完成待頒發變成進行中／反之」並列出姓名，我確認後才執行。
- 已頒章的紀錄不受任何項目修改影響，不回溯、不撤銷。
- 每次修改寫入操作日誌（含修改前與修改後內容）。
- 提供「匯出項目總表為 CSV」「檢查項目總表」「重新載入項目」三個按鈕。

我也可能直接在 Google 試算表修改「項目總表」「級別與章說明」「設定」「告知同意內容」，後端要能容錯：
- 讀取時略過空白列、去除前後空白。
- 項目ID 重複、缺少級別或章名、啟用欄不是是/否時，略過該列，不讓整個系統壞掉，並在後台首頁顯示錯誤列數與列號。

### 7.8 設定（團長專用）
- 畫面列出「設定」分頁的每一項，可修改並立即生效。
- 修改每日排程時間時，自動重裝 trigger。
- 可編輯個資告知同意內容：存檔時產生新版本，舊版本保留。

### 7.9 管理員指定（團長專用）
團長可以在後台指定誰是管理員，不需要知道對方的 LINE userId。提供兩種方式：

方式一：從已綁定的帳號中指定（對方是家長兼服務員時用）
- 列出所有已綁定的 LINE 帳號：LINE 顯示名稱、綁定的小狼姓名。可搜尋。
- 點選某人 → 選角色（團長/服務員）→ 填寫要顯示的姓名 → 確認後立即生效。

方式二：邀請碼（對方沒有小孩在團裡時用）
- 團長按「邀請管理員」→ 選角色 → 填對方姓名 → 後端產生一組一次性邀請碼。
- 邀請碼字元規則同綁定碼但長度多 2 碼，有效時數依設定，只能用一次，與綁定碼不可重複。
- 提供「複製邀請說明文字」按鈕，內容含邀請碼、LIFF 連結與操作步驟。
- 對方開啟 LIFF，在輸入綁定碼的同一個欄位輸入邀請碼，後端辨識為邀請碼後，把他的 userId 寫入「管理員」分頁並帶入預設的姓名與角色。
- 邀請碼輸入錯誤同樣計入綁定失敗次數與鎖定規則。
- 後台可查看尚未使用的邀請碼並作廢。

管理既有管理員：
- 列表顯示：姓名、LINE 顯示名稱、角色、加入時間、指定人。
- 團長可變更角色（團長↔服務員）、修改顯示姓名、移除管理員。
- 系統至少保留一位團長：不可移除最後一位團長，也不可把最後一位團長降為服務員。
- 團長不可移除自己；要卸任須先指定另一位團長，由對方操作。
- 被移除管理員身分後，他綁定的小狼不受影響，仍可用家長身分查詢。

通知與紀錄：
- 指定成功、角色變更、被移除時，推播一則訊息給當事人。
- 有人使用邀請碼成為管理員時，推播通知建立該邀請碼的團長。
- 以上所有操作寫入操作日誌。

第一位團長：
- 系統剛建好、「管理員」分頁是空的時候，由我手動把自己的 userId 填入試算表。請提供「顯示我的 userId」畫面方便我複製。之後的管理員一律從後台指定。

### 7.10 個資處理（團長專用）
針對離團小狼或家長提出要求時使用。兩種處理都要二次確認，並要求我輸入該小狼姓名才能執行。
- 匿名化：把姓名改為「已離團小狼」加流水號、清空小隊、刪除該小狼的所有綁定紀錄、狀態改為已匿名。完成紀錄與頒章紀錄保留，僅供團內統計，無法再對應到個人。
- 完全刪除：從小狼名單、綁定紀錄、完成紀錄、頒章紀錄、通知紀錄中移除該小狼的所有列。操作日誌中與該小狼相關的紀錄，把姓名替換為「已刪除」。
- 刪除或匿名化的操作本身寫入操作日誌，但只記「某團長於某時間處理了一位小狼的個資」，不記姓名。
- 執行前顯示會影響幾列資料；執行後提醒我：既有的每週備份檔仍含這位小狼的資料，會在保留份數輪替後消失，並提供「立即刪除所有舊備份並重新備份」的選項。
- 小狼離團超過設定天數仍未處理時，在後台首頁提醒我。
- 家長端的「解除綁定」只移除該 LINE 帳號的綁定，不影響小狼資料。

## 八、LINE 官方帳號主動通知
觸發時機：

2. 每日排程：依設定時間每天掃全部在團小狼，抓「項目早就全過、今天剛滿晉級間隔」的情況。提供安裝與移除 trigger 的函式。

通知規則：

- 達標超過設定天數仍未頒章 → 再提醒管理員一次，之後不再提醒。
- 推播失敗（未加好友或已封鎖）寫入操作日誌，並在後台首頁標示「通知未送達」。

省推播額度：
- 推播計入每月免費額度，回覆不計。做關鍵字回覆：管理員輸入「可晉級」→ 回覆達標未頒章名單；輸入「快達標」→ 回覆快達標名單；家長輸入「進度」→ 回覆該帳號綁定小狼的摘要與 LIFF 連結。
- 非管理員輸入「可晉級」「快達標」不回名單。
- SETUP.md 說明如何在圖文選單放「查進度」「可晉級名單」按鈕。

## 九、安全與個資（不可妥協）
- 前端只送 LIFF 的 ID token；後端呼叫 LINE 的 ID token 驗證端點並比對 Channel ID，取得 userId。絕不相信前端傳來的 userId。
- 查詢端 API 只回傳該 userId 已綁定小狼的資料。
- 後台每一支 API 都要在後端檢查管理員身分與角色，不能只靠前端隱藏按鈕。指定、變更、移除管理員與個資處理的 API 必須在後端確認操作者是團長。
- API 不回傳其他人的 userId 給前端；需要指認對象時用後端產生的內部代號。
- 綁定碼與邀請碼輸入錯誤達設定次數即鎖定設定的分鐘數。
- 所有金鑰、Channel ID、token、webhook 密鑰、備份資料夾 ID 放 Script Properties，不進版控、不寫進前端。
- 只存孩子的姓名、小隊、入團日與進程紀錄，以及家長的 LINE userId 與顯示名稱。不收集生日、身分證字號、電話、地址、照片。回傳給前端的資料欄位採白名單。
- 沒有同意紀錄就沒有綁定；同意版本過期要重新確認。
- 錯誤訊息不得洩漏其他小狼是否存在，也不得透露輸入的是綁定碼還是邀請碼格式。
- 試算表與備份資料夾只分享給必要的人，不可開「知道連結的任何人」。服務員透過後台操作，不需要試算表的編輯權。
- docs/PRIVACY.md 的告知文字是草稿，請在文件開頭註明「上線前需由團長確認內容，並視需要請教熟悉個資法的人」。

## 十三、工作方式
分階段進行，每個階段結束先停下來向我回報「做了什麼、怎麼驗證的、需要我做什麼」，等我說繼續再往下。每個階段完成都要 git commit，訊息用繁體中文說明變更。

- 階段 0A：git init、存 docs/SPEC.md、建立專案結構、CLAUDE.md、data/items.csv，並列出你對規格的疑問或你認為有風險的地方。
- 階段 0B 技術驗證：只做最小可行的三件事並請我實測 —— ① LIFF 開啟並取得 ID token ② GAS 後端驗證 token 成功，且 token 過期時前端能自動重新登入 ③ LINE webhook 打到 GAS，輸入任意文字能收到回覆。寫一份只涵蓋這三件事的精簡設定步驟給我。三件事全通才往下；任何一件不通，停下來跟我討論替代方案。
- 階段 1：純邏輯函式與 Node 測試，測試全過。
- 階段 2：GAS 後端基礎（setup、設定讀取、ID token 驗證、查詢 API、綁定與告知同意）。
- 階段 3：查詢端前端（告知同意畫面、首頁各區塊、進程頁、技能章頁、我的資料、列印簽核單）。
- 階段 4A 核心後台：首頁、小狼管理、綁定碼、簽核（含小隊批次）、頒章表單、補登、管理員指定的方式一與既有管理員管理、個資處理、備份與權限檢查。同時把 SETUP.md、TESTING.md、PRIVACY.md 寫到足以上線的程度。
- 里程碑一（可上線試用）：階段 4A 完成後停下來。我會實際上線給團裡試用，並回報家長與服務員的使用狀況。在我明確說「繼續做 4B」之前，不要動後面的階段；這段期間只修試用發現的問題。
- 階段 4B 管理介面：項目管理、設定畫面、管理員邀請碼。里程碑一期間，這些需求我會直接改試算表處理，所以第七節 7.7 的試算表容錯必須在階段 2 就做好。
- 階段 5：LINE 主動通知、webhook 關鍵字回覆、每日排程。
- 階段 6：全部文件定稿。

- 改任何功能前先讀 CLAUDE.md、docs/SPEC.md 與相關檔案；改完同步更新 SPEC.md、CLAUDE.md 與 CHANGELOG.md。
- 項目ID 一經產生永不更改、永不重用。
- 不得刪除或重排試算表既有欄位；要加欄位只能加在最右邊，並更新 setup()。
- 除了第七節 7.10 的個資處理功能之外，不得寫任何會覆蓋或刪除「小狼名單」「項目總表」「級別與章說明」「設定」「管理員」「頒章紀錄」「完成紀錄」既有內容的程式。
